# 招投标完整工作流：实训项目需求文档

版本：V1.0　｜　日期：2026-10-13　｜　状态：需求草案，可作为 GitHub 项目立项与任务拆分基线

适用对象：企业招投标、市场、售前、技术、商务、项目管理人员，以及使用 WorkBuddy / AI 编程工具参与实训的学员。

文档定位：面向新建通用招投标实训项目，定义业务模块、协作接口与验收标准。本文中的能力、模板、样例和参考实现均为项目建设要求，实际实现情况以各模块的交付与验证记录为准。

## 1. 项目要做成什么

建设一个可以拆开练、组合跑、检查结果的招投标工作流实训项目。学员负责一个细分模块，使用公开或虚构材料完成业务任务，输出能被下一模块直接读取的文件，最终共同完成一条可回放的业务链。

项目面向企业投标方：发现招标机会，理解招标要求，组织公司资质、人员证书与业绩，编制技术与商务响应，装配标书，完成审查和模拟递交，再记录结果并交给合同与项目团队。首轮使用虚构专业服务项目作为练习载体；行业规则、材料类型和模板通过配置扩展。

项目必须同时体现三种价值：

1. **业务提效**：减少反复找资料、复制人员字段、粘贴证书、检查附件的劳动。
2. **协作提效**：要求、章节、材料、责任人和状态能够传递，不依赖同一个人的聊天记录。
3. **资产复用**：将通用流程、企业规则、模板适配和可复用材料分层，换企业、换项目时能清楚定位要修改的部分。

第一条可见成果是：从招标原文生成有依据的要求和响应矩阵，经过真人确认，把人员与证书装配成可编辑 Word，再输出审核问题与交接记录。完整工作流在此基础上逐步扩展。

### 1.1 本项目的“完整”定义

完整指业务环节与交接责任覆盖完整。首轮实训允许公告来自网页快照、材料库来自本地文件、审批来自确认记录、递交来自模拟回执。每个模块必须写明自己完成了哪一段，不能把本地模拟写成真实平台集成。

完成要求文档、完成实训原型、完成企业生产部署分别验收。本文定义的是实训项目需求，不把生产权限、正式签章和真实递交作为学员首轮任务。

### 1.2 可运行的三条路线

| 路线 | 起点与终点 | 适用情况 | 主要成功标志 |
|---|---|---|---|
| 制作核心线 | 招标材料 → 人员资质章节 → 检查与归档 | 首轮实训，已有投标意向 | Word 可编辑，字段与附件正确，问题可定位 |
| 投标准备线 | 公告 → 筛选 → 决策 → 全本草稿 → 模拟递交 | 后续扩展实训 | 决策有确认，要求有响应，提交版本可追溯 |
| 经营闭环线 | 模拟递交 → 结果回填 → 中标交接 / 丢标复盘 → 资产更新 | 进阶实训 | 结果有证据，承诺可交接，经验可复用 |

“已经决定参与”的项目可以直接进入制作核心线。系统记录业务负责人已有决定，不强迫客户重新经历机会筛选或等待 AI 给出 GO。

## 2. 业务角色与责任

| 角色 | 负责的业务判断 | AI / 程序可以完成的工作 |
|---|---|---|
| 市场 / 销售 | 机会是否值得跟进、客户关系与资源安排 | 采集、去重、规则初筛、机会卡片 |
| 招投标负责人 | 文件版本、投标组织、要求解释与交付范围 | 文件盘点、拆解、矩阵、任务与截止提醒 |
| 技术 / 售前负责人 | 技术路线、服务能力、工期和履约承诺 | 方案草稿、要求覆盖、内容一致性检查 |
| 人力 / 资料管理员 | 人员安排、证书信息、公司资质和业绩授权 | 索引、提取、候选匹配、缺口识别 |
| 商务 / 财务负责人 | 报价、税费口径、付款与商务偏离 | 成本汇总、确定性计算、表格填充、偏差提示 |
| 业务审批人 | 参与决定、最终人员、报价与版本放行 | 接收确认任务、记录意见、查看证据 |
| 递交操作人 | 签章、加密、上传、最终递交与回执核对 | 生成检查清单、准备模拟提交包 |
| 合同 / 项目负责人 | 中标承诺接收、合同差异与执行计划 | 整理交接包、列出差异、生成待办 |

一名学员可以兼任多个角色，但确认记录必须说明是哪种业务责任。模型不能担任业务审批人；测试样例中的虚构审批人只代表模拟记录。

                                              M05 参与决策
                                                     ↓
M06 澄清与变更 ───────────────→ M04/M07及受影响下游
                                                     ↓
                                              M07 响应矩阵与分工
                                                     ↓
M08 企业材料库 → M09 项目材料匹配 ───┬→ M10 技术方案
                                   ├→ M11 商务与资格响应
                                   └→ M12 成本测算与报价
                                               ↓
                         M13 Word与附件装配 → M14 审查与放行
                                               ↓
                                      M15 模拟递交与回执
                                               ↓
                                      M16 结果回填与复盘

## 4. 所有模块共同遵守的标准

### 4.1 一个模块怎样算做完

每个模块有一份机器可读 JSON 和一份中文阅读摘要，摘要应回答：做了什么、依据是什么、还缺什么、谁接手。文件制作模块额外交付可打开的实际文件。

验收针对讲师预先定义的测试集与业务必查项，不以 AI 自述“已完成”或脚本退出码为依据。正常样例证明提效，待确认样例证明责任边界，异常样例证明不会静默产生错误。

### 4.2 处理状态、业务状态、审批状态分开

| 维度 | 建议值 | 含义 |
|---|---|---|
| 模块处理 | `COMPLETE / REVIEW / BLOCKED` | 已完成声明范围 / 需要人复核 / 无法安全继续 |
| 业务参与 | `UNDECIDED / GO / NO_GO / EXISTING_GO` | 是否参与项目，与运行成功无关 |
| 人工确认 | `UNCONFIRMED / CONFIRMED / REJECTED / STALE` | 某项具体内容是否获得确认，版本变化后是否失效 |
| 文档产物 | `DRAFT_READY / PARTIAL_DRAFT / NOT_GENERATED` | 草稿是否生成及覆盖情况 |
| 审查放行 | `DRAFT / CHANGES_REQUIRED / RELEASED / REVOKED` | 指定版本是否满足本次审查范围 |
| 递交记录 | `NOT_SUBMITTED / SIMULATED_SUBMITTED / SUBMITTED_CONFIRMED / FAILED / UNKNOWN` | 模拟或真实回执事实；实训仅使用模拟值 |

`COMPLETE` 不表示“可以正式投标”。上游 `REVIEW` 不禁止下游一切工作：可以生成显式标注缺口的预览，但不能自动选人、形成已批准报价或放行提交。`BLOCKED` 必须说明阻断对象，隔离的问题不能无理由阻断无关模块。

第一期只实现使用到的状态。全局状态词典由 X01 维护，学员不得为同一含义各自创造 `OK / done / 已搞定` 等名称。

### 4.3 输入、证据与版本

- 每个运行声明 `project_id`、`lot_id`、`run_id`、`schema_version` 和输入模式。单标包也填写固定 `lot_id`，首轮只做单标包，多标包属于进阶测试。
- 文件具有 `source_id`、相对路径、版本和文件哈希；所有路径相对于明确输入根目录。不同项目、标包和真实/虚构模式不混用。
- 证据使用 `source_id + 定位 + 原文/可见字段`。PDF 区分文件页序与印刷页码；扫描件保留图片位置或区域说明。
- OCR 与原文抽取保留来源和读取方式。材料索引只是索引，不能冒充已经看过图片；预置结构化 JSON 不能作为“读懂原招标”的唯一证明。
- 日期一律使用 ISO 格式，时刻带时区。分别记录公告发布、报名、澄清、保证金、投标截止等时间，不能合并成一个模糊 deadline。
- 有效期按招标要求指定的基准判断；未指定时列为待确认。历史回放冻结基准日期，不能用运行当天把练习项目全部判过期。
- 缺失值用 `null` 并配 `missing_reason`，数组可为空；不把未知金额填 0，不把未知日期填当天。
- 同一版本重跑，实体 ID 与事实关系保持稳定。文件版本变化后给出条款与资产的映射，不能仅依靠重新编号让全部历史失去关联。

### 4.4 事实、建议与确认

每条业务内容能区分 `SOURCE_FACT`（来源事实）、`PROPOSED`（AI 建议）、`HUMAN_CONFIRMED`（真人确认）。事实变更不自动变成人工确认。

确认记录至少包括：确认对象与版本、确认内容、确认人、时间、结论。确认人由实际用户提供，不能由模型补写；换人、换报价、换模板或收到相关补遗后，受影响确认标为 `STALE`。

公开公告证明公告公开了什么；图片证明可见字段；文件存在证明收到文件。它们都不能单独证明证书真伪、公司实际履约能力或正式任命。

### 4.5 统一交接对象

统一接口建议命名 `bid-training.workflow.v1`。下例是接口设计示意，实际 JSON Schema 由本项目实现并冻结后供各模块使用。

```json
{
  "schema_version": "bid-training.workflow.v1",
  "module": "M04",
  "run_id": "RUN-DEMO-001-M04-001",
  "project_id": "DEMO-BID-001",
  "lot_id": "LOT-001",
  "source_mode": "DEMO",
  "processing_status": "COMPLETE",
  "input_refs": [
    {"source_id": "SRC-001", "relative_path": "tender/tender.md",
     "version": "1.0", "sha256": "<实际文件哈希>"}
  ],
  "scope": {"included": ["人员与资质章节"], "excluded": ["报价"]},
  "issues": [],
  "data": {},
  "next_actions": [{"owner_role": "招投标负责人", "action": "复核拆解结果"}]
}
```

必填公共字段：上例全部顶层字段。问题条目必须含 `issue_id`、`code`、`severity`、`object_id`、`message`、`evidence_refs`、`owner_role`、`next_action`。严重度为 `BLOCKER / MAJOR / MINOR`，与模块处理状态分别记录。

需求、响应、人员、资产、章节、附件、确认记录分别使用稳定 ID。最低追溯链是：

```text
requirement_id → response_id → section_id / field_id
                             → person_id / asset_id → attachment_id
                             → output_file / 输出位置
```

### 4.6 核心 Skill 划分与实现边界

M04、M07、M09、M13 分别实现为要求分析、响应规划、材料匹配和文档装配四个独立 Skill，采用功能型通用命名。M08 提供材料索引，M14 独立审查实际文件。

各 Skill 使用公共信封与模块接口，保留来源和版本；项目/标包字段取自已确认上下文。教师可预置通用参考实现供学员扩展，任务书须列明未实现范围。

### 4.7 可运行与可演示

每个模块必须能读取独立样例运行，也能读取真实上游输出运行；不得暗中读取其他对话或 `examples/expected`。Skill 负责步骤与交互，计算、格式校验、重复判断和文档装配优先使用确定性程序。

所有本轮使用的安装文件、输入、口令和依赖说明须在学习包内。正常样例优先使用一套已适配模板与 3-4 名虚构人员；不以任意模板通用适配作为首轮门槛。

## 5. 18 个业务模块详细需求

下面的验收编号可直接作为 GitHub Issue 的完成条件。数值均为本实训测试集的验收目标，不表示对所有真实业务的准确率承诺。

### M01 公告获取与去重

**目标与负责人**：市场人员一次得到可追溯、去重的机会列表，保留同一项目的不同公告与更新。

**输入**：网页快照、公告文本、公告 PDF 或经授权获取的公开网页；来源配置、抓取日期、已收录记录。首轮使用本地快照。

**输出**：`opportunity_cards.json`、公告原件/快照、采集与失败记录。卡片至少含机会 ID、来源、项目名、采购方、项目编号、区域、业务类型、预算及币种、发布时间、各类截止时间、附件清单和证据。

**规则与人工点**：确定性来源编号优先用于去重，无编号时相似匹配只标疑似重复。同一项目的补遗、新标包和结果公告保留为关联事件。页面不可访问时记录失败，不补造内容。公开网页接入作为进阶适配器，账号登录和真实交易操作不纳入首轮。

**验收标准**：

- M01-AC1：10 份测试公告中，2 份完全重复正确合并；1 份补遗仍保留为独立来源事件。
- M01-AC2：项目名、项目编号、预算和投标截止等预定义关键字段提取正确；未知字段为 `null`，每个已提取关键字段有证据。
- M01-AC3：同一批输入重跑不增加重复机会；相同项目不同标包不误合并。
- M01-AC4：1 份损坏快照有失败记录，其余公告仍能处理；增加一个来源只改配置或适配器。

**实训切片**：为已有输入新增第二种公告格式，证明同样输出能直接交给 M02。

### M02 机会筛选与跟进清单

**目标与负责人**：市场负责人按企业规则筛掉明显不适配项目，把值得进一步判断的项目排成跟进队列。

**输入**：M01 机会卡片、企业筛选规则、分析基准日期。规则可含区域、业务类型、预算区间、准备时间和明确排除条件。

**输出**：`screening_result.json`、中文跟进清单；逐项目记录规则命中、建议状态、理由、优先级、下一动作与负责人。

**规则与人工点**：筛选只回答“值得跟进吗”，不证明“具备全部资格”。未提供企业规则时标 `NOT_EVALUATED`，缺少关键机会信息时转 `REVIEW`。评分如采用权重，权重和阈值来自显式配置。市场人员确认是否继续跟进。

**验收标准**：

- M02-AC1：预设的合适、明确排除、信息不足三组各 2 条，结果全部符合测试规则，逐条列出命中的规则 ID。
- M02-AC2：修改区域或预算配置，无须改代码即可改变相应结果；未触及规则的机会结果不变。
- M02-AC3：缺预算不自动当作低预算，缺资质台账不写“企业不具备资格”。
- M02-AC4：输出含下一步动作与责任角色，可直接启动 M03；回放日期不受当天日期影响。

**实训切片**：新增一条企业筛选规则，展示规则前后的队列变化。

### M03 项目建档与招标文件登记

**目标与负责人**：招投标负责人能确定正在处理哪个项目、哪个标包、哪一套文件，避免漏文件或用错版本。

**输入**：机会卡片或直接上传的招标文件；项目上下文；招标原件、附件、指定格式、补遗与澄清。

**输出**：`project_register.json`、`source_manifest.json`、文件完整性清单。记录项目/标包 ID、当前阶段、负责人、各类时间节点、文件哈希、版本、类型、读取状态与缺失文件。报名、文件获取、保证金、现场踏勘或答疑等动作仅在本项目来源有要求时建立任务，逐项记录完成依据。

**规则与人工点**：用户直接提供文件时允许建档，不依赖 M01/M02。文件名不是唯一标识；已取得招标文件与已确认参与分开登记。无法读出的页数和缺少的附件显式列出；版本优先关系无法确定时请招投标负责人确认。

**验收标准**：

- M03-AC1：招标文件、模板、补遗 3 类文件全部有 source ID、哈希、相对路径和读取状态。
- M03-AC2：同名不同内容文件不会互相覆盖；重复内容能识别；被引用但未提供的附件进入缺口清单。
- M03-AC3：单标包和双标包样例分别归档，其他项目文件不会混入。
- M03-AC4：不可读原件阻断相关范围拆解，未取得补遗确认不自行声明“当前最终版本”。
- M03-AC5：样例中的报名、材料获取与保证金截止分别记录，不因已拿到 PDF 就自动把前置任务标完成；原文没有要求的动作不补造为必需。

**实训切片**：实现文件清单校验，给 M04 提供明确、可复现的输入范围。

### M04 招标要求拆解与证据定位

**目标与负责人**：招投标、售前人员准确掌握“要求是什么、在哪、影响什么”，为响应规划提供结构化依据。

**输入**：M03 文件清单和对应原件；经确认的版本关系；读取范围与分析基准日期。

**输出**：`tender_brief.json`、要求摘要；逐条包含 requirement ID、原文、类别、强制性、否决性依据、评分信息、适用标包、材料要求和证据。类别至少覆盖资格、评分、技术、商务、履约与格式。

**规则与人工点**：区分“必须做”与“未做即否决”，不能一概划成废标条件。评分没有公布则为 `null`，不推测分值。文件冲突分别保留；扫描模糊转人工复核。招投标负责人解释争议条款。

**验收标准**：

- M04-AC1：测试集标注的 12 条必查要求全部检出，包括人员、证书、业绩、报价口径、格式与截止；没有捏造要求或分值。
- M04-AC2：每条要求均能回到具体文件及页/节，定位与原文一致；抽取基于原件，不只读预置 JSON。
- M04-AC3：只读节选时声明覆盖范围；1 组冲突条款保持双方证据并进入复核。
- M04-AC4：相同来源重跑 ID 稳定；补遗修改 1 条时保留旧条款映射，不把历史 ID 分给其他条款。

**实训切片**：在人员节选底座上补拆报价或业绩要求，并交给 M07 落位。

### M05 参与决策与资源安排

**目标与负责人**：业务审批人判断是否投入本次投标，并明确原因、条件和资源约束。

**输入**：M02 初筛、M04 要求、企业资质与资源快照、已有参与决定。M08/M09 尚未完成时只能使用已有材料给出条件性建议。

**输出**：`bid_decision.json`、决策摘要；分开记录 AI 建议、证据完整度、真人最终决定、决定条件、负责人、预计投入和未解决问题。

**规则与人工点**：不强制生成“中标概率”。缺企业资料时可分析招标，不宣称企业合格。已有线下参与决定记录为 `EXISTING_GO`；材料存在明确矛盾时仍提示并阻止相关不实响应。参与决定不能覆盖后续材料、报价或递交确认。

**验收标准**：

- M05-AC1：可参与、不参与、待确认 3 个样例明确区分建议与最终决定，决策依据能回到要求/材料。
- M05-AC2：只有招标文件时不输出“我方全部满足”；缺资源数据不伪造可投入人员。
- M05-AC3：有真实用户提供的已有决定时允许直达 M07；没有确认不能生成“已批准参与”。
- M05-AC4：决定附负责人、条件与时刻；关键需求变更时能产生重新确认任务。

**实训切片**：实现“已有决定登记”和“资料不足的条件性建议”两条分支。

### M06 澄清、补遗与变更影响

**目标与负责人**：招投标负责人看到新补遗后，知道改了什么、哪些输出要更新、谁重新确认。

**输入**：旧版与新版原件、来源登记、当前要求/矩阵/材料/报价/文档引用关系，已有澄清问题与确认记录。

**输出**：`change_impact.json`、待澄清问题草稿、差异与重做清单；包含受影响 requirement、response、section、asset、审批与截止时间。

**规则与人工点**：新文件不是按上传顺序自动覆盖旧文件，覆盖关系依据文件说明或人工确认。用语润色与实质变更分开。问题只生成草稿，由负责人发送。补遗影响资格、人员、工期、价格或格式时，受影响确认置 `STALE`，禁止沿用旧放行。

**验收标准**：

- M06-AC1：一个“人员数量 3→4 + 投标截止后移”的样例准确识别两个变更，列出要求、材料、任务与文档影响。
- M06-AC2：不改未受影响章节；旧版原件与输出可回溯。
- M06-AC3：没有来源依据的覆盖关系进入 `REVIEW`，不自行裁定。
- M06-AC4：已放行草稿收到相关实质补遗后，放行撤回或失效；完成重做与确认前 M15 不能使用旧版本。

**实训切片**：让制作核心链支持一次补遗，证明要求、矩阵、材料与文档联动更新。

### M07 响应矩阵、章节与任务分工

**目标与负责人**：招投标负责人把每条要求落到具体章节、表格、附件和责任人。

**输入**：M04 要求、指定模板与版次、企业分工配置、已有参与决定或本次草稿范围。

**输出**：`response_matrix.json`、`task_plan.json`、章节与缺口清单。响应行包含 response ID、requirement IDs、章节/字段位置、需用材料、填写方式、owner、due time、准备状态和版本依据。

**规则与人工点**：区分指定格式与建议格式；一条要求可对应多个位置，一个位置也可响应多条要求。未提供模板时可生成建议结构，但标为 `SUGGESTED_NOT_VERIFIED`。人员、商务、报价和技术任务分开派发，由负责人确认分工。

**验收标准**：

- M07-AC1：本次范围内所有必需要求有映射；范围外要求有排除说明；没有未知 requirement ID。
- M07-AC2：每行含位置、材料与责任角色；有明确截止要求的任务不晚于相应业务时限。
- M07-AC3：测试模板列名变化时能提示适配差异，不静默填错列；模板版本有记录。
- M07-AC4：下游 M09/M10/M11/M12/M13 可从同一矩阵读到各自任务；全本覆盖与局部覆盖分别统计。

**实训切片**：新增“责任人 + 截止时间”分工，或适配第二套人员表格式。

### M08 企业资质、人员与业绩材料库

**目标与负责人**：资料管理员把分散材料整理成可检索、有版次和使用边界的企业资产。

**输入**：本地文件、虚构证书/资质/业绩材料、人工提供的台账；后续可用授权适配器从企业系统导入。

**输出**：`material_index.json`、已核对字段与来源、重复/过期/冲突清单。资产至少含 asset ID、类型、主体/人员 ID、名称、编号、有效期、版本、文件路径、提取方式、核对状态、使用权限与证据。

**规则与人工点**：材料事实与项目选用分开；建库不等于任命或授权投标。原件保留，修正字段另存核对版。文件名只作线索；同人多证、同名不同人、旧证更新分别处理。公开实训只存虚构或已经允许公开的资料。

**验收标准**：

- M08-AC1：8 份测试材料全部有索引与文件对应；损坏图片和孤立索引能识别。
- M08-AC2：4 张测试证书的预定义可见关键字段提取正确；模糊字段为待核对，不能补数字。
- M08-AC3：新旧同名证书保留不同 asset ID / version；旧版本不会覆盖最新确认版。
- M08-AC4：没有有效期依据的材料不是自动判有效；每个修正字段记录核对来源与确认人。

**实训切片**：做一个文件夹导入器，生成后续 M09 可读取的索引；先以本地导入完成，再挑战系统接口。

### M09 项目材料匹配与人员确认

**目标与负责人**：资料和项目负责人知道哪些候选满足哪条要求，确认本项目使用的人员、资质、业绩和附件。

**输入**：M07 响应矩阵、M08 材料及原文件、拟任角色/人数、有效期基准、用户确认记录。

**输出**：`asset_match.json`、候选与缺口清单、`confirmed_selection.json`。候选状态为 `MATCHED / MISSING / EXPIRED / REVIEW`，附需求 ID、资产 ID、理由和证据；另行保存已确认选用集合。

**规则与人工点**：候选匹配与正式选用分开。未收到真人确认保持 `REVIEW`；姓名、编号、资格、期限或使用权限冲突进入复核。选择不存在的 ID 阻断。换人和换证必须更新人员、附件和确认，不沿用旧签认。

**验收标准**：

- M09-AC1：4 人/4 证样例列出正确候选；未确认时确认人为空，不能流入已确认装配分支。
- M09-AC2：确认 3 人后，下游只收到被确认的 3 人及其对应资产，具有姓名、时间和确认版本。
- M09-AC3：过期证、重名冲突、未知 asset ID 三类异常不会被标成已满足。
- M09-AC4：把一名项目人员替换后，变化能传给 M13；旧选用记录保留，旧材料不混进新输出。

**实训切片**：从仅匹配人员证书扩展到公司资质或业绩，同时保留人工确认。

### M10 技术方案与服务承诺编制

**目标与负责人**：技术/售前负责人得到紧扣本项目要求、可复核的技术章节草稿，避免泛泛而谈。

**输入**：M04 技术与履约要求、M07 分工、M09 已确认资源、企业方法与已批准案例、工期和服务边界。

**输出**：`technical_response.json`、章节草稿；按 section ID 记录正文、对应要求、引用材料、事实与建议、承诺事项、待确认内容。

**规则与人工点**：至少覆盖工作方法、实施步骤、人员职责、计划、交付物和质量安排中本项目实际要求的部分。设备数量、资历、业绩、响应时限和工期不能无来源编造。流程安排可以建议，但进入已确认响应前必须由技术负责人确认。

**验收标准**：

- M10-AC1：限定一个技术章节的 5 条测试要求全部有回应位置，且可定位原要求。
- M10-AC2：不存在凭空的企业业绩、认证、人员经历或设备能力；缺资料列待确认。
- M10-AC3：测试工期、角色和交付物与已确认资源一致，故意设置的工期冲突可检出。
- M10-AC4：输出可由 M13 装入指定章节；未确认承诺在审查清单中可识别。

**实训切片**：编制一个“实施计划与交付物”章节，用换工期或换人员测试联动更新。

### M11 资格、商务文件与偏离响应

**目标与负责人**：商务人员快速形成资格表、商务响应、声明与偏离清单，保持与原件和授权一致。

**输入**：M04 资格/商务要求、M07 指定格式、M09 选用材料、企业已确认基础信息、用户提供的商务立场。

**输出**：`commercial_response.json`、表单草稿、商务偏离清单与签署待办；每项关联 requirement、表单/字段位置和依据。保证金/保函如有要求，登记金额、形式、期限、付款或出具证据与责任人；没有凭证时保持待办。

**规则与人工点**：已存在资质从材料库引用；授权代表、无不良记录等声明由有权人员确认。付款、责任、担保和服务边界没有提供立场时不能自动承诺“完全响应”。签字和盖章仅列操作位与待办，不制造签章对象。

**验收标准**：

- M11-AC1：一套测试表单的必填项全部有真实测试来源或明确缺口；不改原定表头。
- M11-AC2：设置的一条商务偏离准确出现在偏离表和待确认清单，不能默认“无偏离”。
- M11-AC3：未取得声明与授权确认时不写“已签署”；缺章位有提示。
- M11-AC4：名称、项目编号、期限与其他章节一致，输出可供 M13 读取。

**实训切片**：制作一张资格材料表与一张商务偏离表，展示事实填充和业务承诺的差别。

### M12 成本测算、报价与审批

**目标与负责人**：商务/财务负责人得到口径明确、计算一致、可审批的项目报价草稿。

**输入**：明确提供的工作量、成本参数、数量、单价、税费口径、招标限价、币种、舍入规则和报价模板；这些参数均为本次练习显式输入。

**输出**：`pricing_result.json`、成本/报价明细、报价表草稿、审批请求；保留计算表达式、输入值、汇总口径、版本、待确认项。

**规则与人工点**：金额计算用 Decimal 等确定性计算，不能交给模型口算。税率、含税/不含税、折扣与舍入规则不凭空设定。总价、分项价、报价函一致；最终报价由财务/业务审批人确认，模型不自行定价。可退保证金按资金占用单列，不能自动计成服务成本；是否计入费用遵循给定成本规则。

**验收标准**：

- M12-AC1：3 组固定计算样例的数量×单价、汇总和明确给定税费公式结果与期望值一致，精度按测试规则。
- M12-AC2：缺税费口径、报价超过输入限价、分项与总价不一致均产生对应问题。
- M12-AC3：报价变更后旧审批标失效；未确认报价不进入放行包。
- M12-AC4：导入 M13 后报价表与报价函数值一致，记录每一版审批对象的哈希/版本。

**实训切片**：实现报价表计算与一致性检查，用一次单价变化证明联动。

### M13 Word、表格与附件装配

**目标与负责人**：招投标制作人员得到可编辑、格式对应、附件正确的 Word 文档。

**输入**：M07 响应矩阵与模板 manifest、M09 已确认材料、选定范围内 M10/M11/M12 的内容、已确认项目字段和原文件。

**输出**：实际 DOCX、`assembly_result.json`、来源与待确认清单；记录章节、字段、表格、图片、附件与输出位置对应关系。

**规则与人工点**：只接受声明支持的模板和版次。首轮范围为人员资质局部章节；未制作章节列出，不宣称全本已完成。确认字段确定性填入；未确认建议可进入标注清楚的预览，未确认人员不能作为选定人员自动装配。每次生成到新输出目录。

**验收标准**：

- M13-AC1：DOCX 能用文档软件打开并编辑；人员表字段、附件图片与 manifest 的目标位置一致。
- M13-AC2：确认的 3 人/3 证准确填入；换一人后新姓名/编号/图片同步改变，旧姓名、旧编号及旧图片哈希不残留。
- M13-AC3：模板哈希不符、缺图片、跨项目/标包和路径越界均被拒绝或明确阻断相关输出。
- M13-AC4：渲染预览检查没有遮挡、裁切、缺图；声明范围内无未处理占位符，全本未制作部分显式标为未完成。
- M13-AC5：实际生成文件与 JSON 记录一致；只交 Markdown 或截图不能替代 DOCX。

**实训切片**：在已支持模板上增加一列或一个附件类型；任意模板适配作为后续挑战。

### M14 要求覆盖、审查整改与版本放行

**目标与负责人**：审核人知道哪些问题已查、在哪里、由谁改，并对指定版本作出放行判断。

**输入**：M04 原要求、M07 矩阵、原始材料、已确认内容、M13 实际文档及版本、审查规则与人工意见。

**输出**：`review_result.json`、问题整改清单、`release_record.json`；每个问题包含规则、严重度、具体文档位置、依据、责任人、修复状态和复核记录。

**规则与人工点**：审查实际产物，不只审查生成程序日志。至少检查要求覆盖、项目字段一致、人员与附件、数字口径、占位符、模板版次、未确认承诺。局部审查只放行局部草稿，不放行整本递交。重大问题关闭由规则复测或真人复核提供依据。

**验收标准**：

- M14-AC1：核心线中的漏附件、错项目名、旧人员、残留占位符 4 项注入问题全部检出并定位；接入报价后，再增加总价不一致，第 5 项也须检出。
- M14-AC2：覆盖统计分母为声明范围内应覆盖要求，未读章节和全本未覆盖项单列，不产生虚假的全本 100%。
- M14-AC3：修正一个问题后只在复测通过时关闭；未解决 BLOCKER 不能进入 RELEASED。
- M14-AC4：放行记录绑定文档哈希、范围和人；文件被修改后旧放行失效，M15 不接受旧记录。

**实训切片**：独立做一个审查 Skill，读取别组生成的 Word，找出预置的一个错误并复测整改。

### M15 模拟递交、开标与澄清跟踪

**目标与负责人**：递交操作人确认“准备提交的是哪一版、还缺什么、是否收到回执”，招投标负责人跟踪开标与后续澄清，完成本地模拟流程。

**输入**：已放行的全本模拟包、版本哈希、提交要求、操作者、模拟时间及平台回执样例；按项目需要提供开标记录、解密结果、述标安排或评审澄清请求。

**输出**：提交清单、固定版本的模拟 ZIP、`submission_record.json`、`opening_record.json`、回执对账结果与澄清答复草稿；包括项目/标包、提交版本、附件数量、模拟时刻、回执 ID、开标/解密状态、问题来源、答复期限、负责人和结果。

**规则与人工点**：课堂不登录真实交易平台、不执行签章或真实上传。真实操作始终由有权人员完成。成功生成 ZIP 不等于成功递交；没有可核对回执时为 `UNKNOWN / NOT_SUBMITTED`。人员章节的局部包可以演示打包，但不能伪装全本递交。澄清答复依据原提交内容，由负责人确认；不得自动改变已批准报价或承诺。开标成功不等于中标。

**验收标准**：

- M15-AC1：全本模拟输入有有效放行、文件齐全且时间符合固定测试条件时，产出 `SIMULATED_SUBMITTED` 和对应回执记录。
- M15-AC2：局部范围、失效放行、文件哈希变化或缺少要求的附件均不能获得完整提交状态。
- M15-AC3：超出模拟截止、回执项目不符、回执失败三个样例均正确识别；无回执不猜成功。
- M15-AC4：同一个提交包重试不重复登记成功提交；明确标注演示模式，保留失败记录。
- M15-AC5：一份模拟评审澄清能关联原提交版本、答复期限与责任人；未确认答复不标为已发送，开标记录不被当作中标证据。

**实训切片**：先做模拟平台适配器核对准备包与回执，再增加一条开标或澄清跟踪任务。

### M16 结果回填与中标/丢标复盘

**目标与负责人**：市场与招投标负责人形成可靠结果台账，分清公告事实和原因假设。

**输入**：结果公告/通知、M15 提交记录、我方报价与评分（如已提供）、企业历史台账、复盘意见。

**输出**：`bid_result_record.json`、`retro_report.json`；记录 `WON / LOST / PENDING / CANCELLED / WITHDRAWN / NOT_PARTICIPATED`、中标方、公告金额与范围、我方价格、评分、证据、确认人和后续动作。按实际提供的条件生成保证金退回跟踪、结果核对或异议处理待办，不自行给出规则之外的期限或对外发出主张。

**规则与人工点**：候选公示与最终结果分开；未找到公告不是丢标。公告总金额不得自动当作单标包金额或合同金额。丢标原因只有证据支持时才记为事实，否则是待确认假设。复盘统计声明分母与时间范围。

**验收标准**：

- M16-AC1：中标、丢标、待公布、取消、未参与的测试记录正确分类，关键字段有结果来源。
- M16-AC2：4 个确认参投结果中 2 中标、2 丢标，另有 1 待定、1 取消、1 未参与时，中标率明确为 2/4=50%；其他类别分别列出，不混入分母。
- M16-AC3：无评分或对手报价时不补造；“价格导致丢标”等缺证据理由不写为确定事实。
- M16-AC4：结果更新与重复公告不会重复计数；中标记录交 M17，全部结果交 M18。

**实训切片**：从一份结果公告生成可回填记录，加入一条严格区分事实与假设的复盘。

### M17 中标后合同与项目交接

**目标与负责人**：合同与项目负责人接收到准确的投标承诺，知道签约和启动时必须核对什么。

**输入**：已确认中标结果、实际放行/提交的标书版本、已确认报价、履约与服务承诺；合同草案如已提供。

**输出**：`handover_package.json`、承诺台账与差异清单；包含范围、人员、工期、交付物、价格、付款、保障事项、证据、负责人和接收状态。签约、履约担保、保证金转换等后续动作依据实际提供条款登记为任务与凭证要求。

**规则与人工点**：以实际提交版本为依据，不从后来修改的草稿提取承诺。合同已提供时做对应比较，没有合同则列待取得，不替客户生成最终合同约定。中标不等于已签约，也不等于项目已启动；接收人确认交接，合同与项目系统为后续接口。

**验收标准**：

- M17-AC1：中标样例的范围、金额、人员、工期和交付物可回溯到对应公告/提交文件。
- M17-AC2：合同草案中植入的 2 个承诺差异检出并定位；没有草案不宣称完成合同一致性检查。
- M17-AC3：待定、丢标、取消记录不会生成已确认中标交接；接收人为空时交接状态未完成。
- M17-AC4：输出可由后续合同或项目模块接收，保留提交版本与来源引用。

**实训切片**：用一份模拟合同承接投标承诺，完成一次差异核对。

### M18 全过程归档、资产沉淀与复用

**目标与负责人**：招投标负责人能回放项目过程，资料管理员能提取经批准的复用资产。

**输入**：所有模块的原件引用、输入输出、确认、放行、递交、结果与复盘；公开/内部材料标记和复用许可。

**输出**：`archive_manifest.json`、归档包、`reuse_candidates.json`；归档含文件列表、版本、哈希、运行与状态关系，复用候选含适用场景、来源、批准人和失效条件。

**规则与人工点**：从首个模块开始记录，不等最后才找文件。项目专属信息与通用方法分开；含价格、人员或客户信息的内容先标权限和适用范围。模板、章节草稿只有经人批准后进入复用库，AI 自评“高质量”不等于可复用。

**验收标准**：

- M18-AC1：制作核心线的每份输入、输出和确认均能从 manifest 找到，哈希核验无缺失。
- M18-AC2：换人或补遗前后两版都可回放；重跑不覆盖已归档历史。
- M18-AC3：至少提取 1 个模板适配、1 条规则和 1 个脱敏章节作为待批准复用候选，写明范围。
- M18-AC4：未批准候选不能自动进入下次已确认响应；公开导出包只包含明确可公开材料。

**实训切片**：制作可回放的项目目录索引，给下一次练习复用一项批准资产。

## 6. X01 公共底座与协作要求

X01 是支撑各组的公共能力，由教师或承担底座任务的小组维护。首轮用目录和 JSON 即可，数据库、Web 界面、权限服务均可后置。

| 能力 | 工作目标 | 最低验收标准 |
|---|---|---|
| 接口校验 | 上下游直接交接 | 校验公共字段、模块字段、项目/标包和 ID 引用；错误字段有明确路径 |
| 运行与版本 | 可重跑、可回放 | 每次运行有唯一 run ID；旧输出保留；同输入实体关系稳定 |
| 证据引用 | 判断可核对 | source ID 都能解析到提供的文件与定位；不能引用不存在原件 |
| 人工确认 | AI 建议有业务接管 | 保存确认对象、版本、人、时间；变更后可失效 |
| 流程调度 | 正常、缺失与阻断都能推进 | 已完成模块可跳过；明确决定可登记；只重跑受影响模块 |
| 配置与适配 | 换企业/模板可定位改动 | 企业规则、字段映射与来源适配从通用逻辑分离 |
| 模式与数据隔离 | 课堂可放心复现 | 默认 DEMO；真实输入不自动回退样例；输出保留 source mode |
| 观察记录 | 学员遇错能排查 | 日志至少含模块、运行、阶段、状态、耗时与错误；无密钥或完整敏感原文 |

建议逻辑层级：

```text
通用层：状态、文件读取、字段校验、证据、日期/金额计算、Word装配
企业层：企业规则、角色、材料字段、模板映射、批准素材
来源层：网页快照、本地材料、模拟平台回执、后续真实系统适配
教学层：独立样例、挑战题、参考答案、验收规则与路演材料
```

跨模块变化以 `change_impact` 记录为准。最低必须验证三个联动：人员替换影响表格与图片；模板变更影响落位与装配；报价变更影响报价表与审批。不能把“重新运行全部”作为唯一变更策略。

## 7. 首轮 MVP 与后续扩展

### 7.1 首轮制作核心线

采用 M03 → M04 → M07 → M09 → M13 → M14 → M18，M08 提供本地材料索引。先建设可运行的核心模块与通用参考实现，再由学员扩展模块能力。

首轮数据限制：1 个项目、1 个标包、1 套已支持模板、4 名虚构人员、4 张证书、1 个正式生成范围为“人员资质章节”的草稿。全本技术、商务与报价不在这条线的完成条件中。

共同演示：

1. 读取原招标节选，生成可追溯要求。
2. 将要求映射到模板和责任人。
3. 核对材料，给出 4 人候选，真人确认其中 3 人。
4. 生成含表格和 3 张对应证书的可编辑 Word。
5. 审查实际 Word，并归档通过范围与待办。
6. 替换 1 人，重新确认与生成，证明旧姓名、旧编号、旧图片不残留。

首轮每组至少完成一个分配到本组的功能或扩展任务。例如 M04 增加业绩要求，M07 增加责任和期限，M08 增加证书导入，M09 增加公司资质匹配，M13 适配新列，M14 独立审查实际 Word。若使用教师提供的参考实现，每组须展示新增能力或新输入验证，不能仅复制运行同一套样例。

### 7.2 扩展优先级

| 阶段 | 新增内容 | 对学员/业务的价值 | 完成标志 |
|---|---|---|---|
| A：制作底座 | 首轮核心线 | 尽快获得可见成果 | 可编辑 Word、人工确认、换人联动、局部审查 |
| B：准备闭环 | M06、M10、M11、M12 | 接近真实标书制作 | 补遗联动、一章技术方案、一套商务表、一套报价 |
| C：经营闭环 | M01、M02、M05、M15、M16、M17 | 连接市场、制作与交付 | 快照获客、决策登记、模拟回执、结果复盘和交接 |
| D：企业试点 | 按需求接真实来源、资料与审批系统 | 验证企业实际提效 | 另立部署/权限/真实数据/正式操作验收范围 |

阶段 C 的 M15 只有在选定的全本模拟范围完成与放行后才能演示完整递交。资料不足时可以独立样例实训，不能把制作核心线的局部章节强行称作整本标书。

## 8. GitHub 项目怎么拆

### 8.1 推荐仓库布局

建议独立仓库名为 `bid-workflow-lab`。项目代码、样例、配置、Skill 和文档采用通用命名。本稿提供结构建议，不代表已创建或发布 GitHub 仓库。

```text
README.md                         新学员从这里开始
docs/
  requirements.md                 本需求文档
  glossary.md                     术语、状态与ID说明
  interfaces.md                   公共字段与模块接口
  quickstart.md                   安装、依赖、运行与排错
  tasks/M01.md ... M18.md          每组的任务书、输入、口令、验收
schemas/                          公共与模块JSON Schema
skills/                           学员使用或新增的Skill
src/core/                         公共处理与装配能力
src/modules/                      18个模块实现
adapters/                         来源格式、快照与模拟平台适配
configs/generic/                  通用虚构企业配置
configs/clients/demo-company/     示例客户映射与规则
templates/                        已声明支持的模板
samples/modules/Mxx/
  normal/                         完整正常输入
  review/                         需要人判断的输入
  abnormal/                       冲突或损坏的输入
samples/e2e/                      核心线、补遗、全本模拟、结果回填
tests/contracts/                  字段、ID、引用与状态校验
tests/modules/                    模块客观规则与回归用例
tests/e2e/                        串接与变更验证
outputs/                          本地输出，默认不提交
examples/approved-outputs/         教师批准的公开参考结果
.github/ISSUE_TEMPLATE/            模块任务、缺陷和验收记录
.github/pull_request_template.md   变更、证据和联动说明
```

脚手架具体目录可以调整，但须有明确入口、模块独立输入和公共接口。实际运行命令在实现选型后由教师给出，不要求学员猜测本稿中的建议目录已经存在。

### 8.2 每个模块对应一个可领取的 Issue

Issue 必须含以下字段，可从第 5 节复制后补具体样例：

```text
模块ID与名称：
业务目标与本次范围：
业务负责人 / 开发负责人 / 验收人：
依赖模块与接口版本：
输入目录与必需文件：
输出目录、JSON对象和阅读摘要：
本组负责的功能 / 相对通用参考实现新增什么：
正常案例 / 人工复核案例 / 异常案例：
验收编号与对应检查方法：
演示口令与安装步骤：
人工确认点及确认记录：
未包含的范围与下一组交接：
完成证据位置与PR：
```

复杂模块拆成相邻 Issue，例如 M08“文件盘点→证书字段提取”、M13“表格填充→证书附件装配”。拆分后仍共享同一个接口，不让两个学员各自生成无法合并的材料格式。

### 8.3 每个 PR 的最低交付

1. 实现或 Skill、配置、独立样例与中文操作卡；首次搭建时一并提供必要依赖。
2. 至少 1 正常、1 REVIEW、1 异常运行；输出 JSON 能通过本次接口校验。
3. 展示本组负责的功能或新增能力，且实际读取自己的输入；不得预先复制参考答案作为运行结果。
4. 用至少一次上游实际生成文件运行下游，不只用固定 fixtures。
5. 提供日志、关键输出和至少一张可证明结果的截图；截图不能替代 JSON / DOCX。
6. 写明人工责任与未实现范围；检查包内相对路径、公开数据与安装复现。

教师参考答案单独保存，正常运行不可访问；另备不提供答案的变更输入检验泛化。实训可使用公开正常样例，但以更换参数、证书或模板后的实际结果证明贡献。

## 9. 样例、测试与总体验收

### 9.1 样例必须覆盖的业务变化

| 编号 | 样例 | 预期结果 | 验证重点 |
|---|---|---|---|
| E01 | 正常人员资质制作 | 3 人/3 证，局部 Word 草稿可用 | 正向提效与证据链 |
| E02 | 尚未人工确认 | REVIEW，可看候选，不做确认版装配 | 人工接管 |
| E03 | 证书模糊或过期 | 原因明确，冲突项不能算已满足 | 提取与有效性边界 |
| E04 | 临时换人 | 新人/新证同步更新，旧内容无残留 | 数据、正文、表格、附件联动 |
| E05 | 补遗把人数 3 改为 4 | 原确认/放行受影响失效，重新补人 | 版本与变更传播 |
| E06 | 同名文件或不同标包 | 不覆盖、不误合并、不交叉使用 | 文件与项目隔离 |
| E07 | 模板换列或版次 | 要求重新映射，不能静默填错位置 | 模板适配 |
| E08 | 报价口径缺失或超限 | 待确认/阻断放行，无假定税费 | 计算与审批 |
| E09 | 实际Word注入4个局部错误；报价接入后增至5个 | 范围内全部定位，修正后可复核 | 独立审查实际产物 |
| E10 | 全本模拟与回执 | 只在齐备、放行、回执正确时模拟成功 | 递交事实与状态 |
| E11 | 中标/丢标/待定/取消 | 分开回填，统计分母正确 | 经营结果 |
| E12 | 中标交接与合同差异 | 承诺可追溯，差异列待办 | 销售到交付交接 |

所有样例使用虚构企业、虚构人员、虚构证书与固定分析日期。历史公开招标文件只能作为明确标注的回放输入，不能与虚构企业材料一起写出真实资质结论。

### 9.2 判断模块质量的客观指标

- 关键要求检出率：检出的标注必查要求数 / 应检必查要求数，核心固定样例目标为 100%。
- 证据有效率：可回到正确原文件位置的引用 / 输出引用总数，固定样例目标为 100%。
- 响应覆盖率：有有效响应位置的范围内必需要求 / 范围内必需要求总数；全本未覆盖另报。
- 材料对应正确率：已选人员、字段、证书与附件的正确对应 / 预期对应，固定样例目标为 100%。
- 关键异常检出率：检出的指定 BLOCKER / 注入 BLOCKER 总数，固定样例目标为 100%。
- 重跑一致性：同输入的业务实体、匹配、计算与引用关系一致；自然语言措辞允许不同。

没有强制所有输出逐字一致。LLM 自由文本用必查事实、引用和禁造字段验收；金额、状态、ID、文件内容与附件哈希用程序检查。文档版式由实际渲染验收。

### 9.3 全项目交付门槛

首轮核心线只有在以下条件同时满足时通过：

1. 新学员从 README 能定位安装、样例、口令和输出，全部路径不依赖教师电脑。
2. 8 个核心模块能力（含轻量 M03/M08/M18）按声明范围完成，每份 JSON 均通过公共/模块接口校验。
3. 至少一次直接使用上游产物串联 M04 → M07 → M09 → M13 核心制作，并归档审查记录。
4. 实际 DOCX 能打开、编辑、显示表格和正确证书；正常与换人场景均通过。
5. E01-E04 与 E09 的 4 项局部错误检查通过；总价错误和其他样例随对应模块阶段纳入验收，不假称已测。
6. 有业务确认记录、版本、问题和接管责任；每组有至少一项新增能力。
7. 独立运行、WorkBuddy 实机运行、整链运行分别记录证据；Python 测试通过不冒充实机成功。

扩展到阶段 B/C 时，除模块各自验收外，必须分别通过补遗联动、技术商务报价装配、全本模拟回执、结果回填与中标交接对应场景。仅展示预生成结果须明确标回放。

### 9.4 建议实训评价权重

| 维度 | 权重 | 评价问题 |
|---|---|---|
| 业务结果正确 | 30% | 是否真正解决任务，正常结果是否可用 |
| 上下游交接 | 20% | 别组能否直接读取输出，ID和范围是否一致 |
| 来源与事实 | 15% | 能否找到依据，是否出现编造或无依据确认 |
| 变化与异常处理 | 15% | 换数据后能否处理，问题是否交给正确的人 |
| 安装复现与说明 | 10% | 另一名学员是否能按卡片跑通 |
| 新增能力与业务讲解 | 10% | 完成了哪些功能或扩展，能否说明提效价值 |

这是建议的教学评分，不是必须上线的系统功能。核心正确性错误不能靠其他分项得分抵消；先修复错误再评优。

## 10. 建设顺序与教师准备

### 10.1 建仓前完成四件事

1. 确定首轮选“制作核心线”，将第 7.1 节范围写进 README；18 个模块进入路线图，不要求一次全部完成。
2. 冻结公共字段与状态，教师提供本项目基础样例、模板、公共底座与可用参考结果。
3. 每组领取一个有明确新增能力的 Issue，并指定业务判断人和验收人。
4. 教师预跑正常核心线，保存实机证据；准备一套参数不同的挑战输入验证学员模块。

### 10.2 推荐实训节奏

第一轮先展示正向结果，各组理解输入输出，做一个新增切片并串接。第二轮再换人、换模板、加补遗、缺证书，要求学员解释状态变化和谁接管。异常处理用于理解流程，不让整场实训围绕排错展开。

进阶学员可以领取 M06、M10、M12 或 M16，因为它们分别引入版本联动、内容编制、确定性计算和经营数据，容易形成独立、可展示的模块成果。

### 10.3 暂定规则与待业务确认事项

以下均不影响虚构样例启动；迁移到具体企业时需替换为企业提供的真实规则。

| 待确认项 | 影响模块 | 首轮默认做法 |
|---|---|---|
